# 基于多智能体协作的高考志愿智能填报系统研究

> 本项目为本科毕业设计，旨在设计并实现面向高考志愿填报场景的智能决策辅助系统。系统仅提供志愿填报参考和风险提示，不保证录取结果；招生政策、招生计划和录取数据应以各省教育考试机构、院校招生官网及教育部阳光高考等官方渠道发布的最新信息为准。

## 1. 项目介绍

### 研究背景

高考志愿填报需要综合考量考生成绩、全省位次、选科组合、专业兴趣、目标城市、院校招生计划和历年录取情况等多项因素。现有服务虽可提供院校专业查询或数据推荐，但在多因素个性化分析、推荐过程解释和方案风险复核方面仍有提升空间。

### 建设目标

本项目拟利用大语言模型理解考生需求，通过多智能体协作完成考生画像构建、任务规划、数据检索、院校匹配、志愿推荐和风险评估；结合结构化招生数据、规则与加权评分方法以及 RAG 检索增强生成能力，生成具有推荐理由、数据依据和风险提示的“冲、稳、保”志愿方案。

### 主要解决的问题

- 将分数、位次、选科、兴趣、城市偏好和风险偏好等信息整理为可用于决策的考生画像。
- 对院校、专业、招生计划及历史录取信息进行多条件检索和匹配。
- 在推荐过程中兼顾录取机会、专业偏好、选科限制和地域偏好，并给出可解释的结果。
- 对选科要求、数据完整性和志愿梯度分布进行二次核验，识别潜在风险。
- 通过政策知识库问答，为招生政策、招生章程和专业介绍等文本资料提供检索依据。

## 2. 技术栈

| 类别 | 技术与规划用途 |
| --- | --- |
| 后端 | Python、FastAPI、Uvicorn；已提供考生、招生数据查询与方案草稿接口。 |
| 多智能体 | LangChain、LangGraph，用于封装 Agent 能力并编排协作工作流、条件判断和有限次数的调整。 |
| 大语言模型 | 预留兼容 OpenAI 的 API 配置；当前本机尚未接入真实模型，工作流使用确定性规划和解释，不能视为 LLM 效果验证。 |
| 关系型数据库 | MySQL，用于存储院校、专业、招生计划、历史录取数据和方案记录等结构化数据。 |
| 数据库连接 | PyMySQL + DBUtils 连接池；使用参数化 SQL，不使用 SQLAlchemy 或其他 ORM。 |
| 向量数据库 | Chroma，用于持久化政策、招生章程和专业介绍等知识库文本的向量索引。 |
| 前端 | HTML5、CSS3、原生 JavaScript；静态页面由 FastAPI 同源提供，使用 `fetch()` 调用业务 API，无前端构建工具。 |
| 知识库 | RAG（检索增强生成），用于对非结构化招生与政策资料进行解析、分块、向量化、检索和辅助回答。 |

## 3. 系统功能模块

### 考生信息管理

录入并校验考生所在省份、报考年份、高考成绩、全省位次、选科组合、专业兴趣、目标城市及风险偏好等信息，形成结构化考生画像。

### 院校专业数据查询

管理和查询院校基本信息、专业信息、招生计划及历史录取数据；支持按省份、年份、院校、专业和选科要求等条件筛选，并记录数据来源、适用年份和更新时间。

### 智能志愿推荐

综合考生位次、选科要求、专业兴趣和城市偏好，对院校专业进行筛选和加权评分，生成“冲、稳、保”分层方案，并展示推荐理由与数据依据。

### 风险评估

对候选方案进行二次检查，重点评估选科限制、数据完整性和志愿梯度分布，输出风险提示与调整建议。

### 政策知识库问答

基于 RAG 检索招生政策、院校招生章程和专业介绍等文本，为用户提供有知识库依据的问答与辅助解释。回答应标明检索来源或适用范围，不能替代官方政策解读。

### 历史方案管理

保存考生历史分析方案及其生成时间、推荐结果和风险提示，支持按考生查询、查看详情及两份方案的页面对比。

## 4. 多智能体设计

系统由 LangGraph 编排以下六个 Agent 的协作流程：

| Agent | 职责 |
| --- | --- |
| 考生画像 Agent | 校验、整理考生输入信息，生成标准化考生画像，并识别缺失或异常字段。 |
| 任务规划 Agent | 根据考生需求拆分分析任务，确定后续检索、匹配、推荐和复核的执行顺序及所需条件。 |
| 数据检索 Agent | 查询 MySQL 中的结构化招生数据，并从 Chroma 知识库检索相关政策与文本资料。 |
| 院校匹配 Agent | 基于位次、选科要求、专业兴趣和城市偏好筛选院校专业，计算或整理匹配候选集。 |
| 志愿推荐 Agent | 综合匹配结果和规则评分，生成“冲、稳、保”志愿方案，说明推荐理由和数据依据。 |
| 风险评估 Agent | 复核选科限制、数据时效与完整性、方案梯度等风险，输出风险等级、提示和调整建议。 |

## 6. 环境配置与运行说明

当前提供 FastAPI 基础业务接口、RAG 知识库、六 Agent 工作流与 MySQL 脚本。以下命令以 Windows PowerShell、项目根目录为起点。

### Python 环境

- 使用 Python 3.12（最低要求 Python 3.10），在项目根目录建立 `.venv` 并安装当前阶段依赖：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

LangChain、LangGraph、Chroma、PDF/DOCX 解析及文件上传依赖均已列入 `requirements.txt`。

### MySQL 配置

- 当前机器使用 MySQL Community Server 9.7.4，`MySQL97` 服务已运行，配置文件为 `C:\ProgramData\MySQL\MySQL Server 9.7\my.ini`，端口为 3306。旧的 `MySQL94` 服务与本项目无关。
- 在根目录 `.env` 中填写 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASSWORD` 和 `DB_NAME`；`DB_NAME` 当前固定为 `gaokao_agent`，建库账号需具备 `CREATE DATABASE`、建表及插入权限。后续运行服务建议改用最小权限账号。
- `sql/schema.sql` 包含 13 张表的建库和建表语句；`sql/seed_simulated_data.sql` 是可选的**模拟数据**初始化脚本，不含官方招生数据。
- 服务启动后使用 DBUtils 有界连接池管理 PyMySQL 连接，写事务完成后提交或回滚，连接归还池中。

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m scripts.database init
..\.venv\Scripts\python.exe -m scripts.database seed
..\.venv\Scripts\python.exe -m scripts.database check
```

`init` 建库建表，`seed` 导入模拟数据，`check` 检查连接、数据库是否存在及 13 张预期表是否齐全。以上步骤已在 MySQL 9.7.4 上执行并验证；`seed` 重复运行不会增加示例记录。连接失败时先检查 MySQL 服务和 `.env`，不要将密码发送到聊天或提交仓库。

### 环境变量配置

根目录 `.env.example` 列出了数据库、日志及模型配置。本地 `.env` 已被 `.gitignore` 忽略；不要将真实密钥提交至仓库或发送到聊天中。模型使用兼容 OpenAI 的 HTTP API，地址填写到 `/v1` 等 API 根路径，不包含 `/embeddings` 或 `/chat/completions`：

| 变量 | 用途 |
| --- | --- |
| `EMBEDDING_API_BASE_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL` | 文本与问题向量化；调用 `POST {BASE_URL}/embeddings`。 |
| `LLM_API_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` | 基于检索片段生成答案；调用 `POST {BASE_URL}/chat/completions`。 |
| `MATCH_RANK_WEIGHT`、`MATCH_INTEREST_WEIGHT`、`MATCH_CITY_WEIGHT`、`MATCH_RISK_WEIGHT`、`MATCH_DATA_WEIGHT` | 推荐评分的五项权重，默认 50、15、10、10、15，合计必须为 100。 |
| `MATCH_REACH_RATIO`、`MATCH_SAFE_RATIO` | 冲/稳和稳/保的位次比值分界，默认 0.9、1.2，前者必须小于后者。 |

也可以在本机访问 `http://127.0.0.1:8004/static/pages/models.html`，通过“模型连接”页面分别填写问答模型和 Embedding 的 API 密钥、基础网址与模型 ID。点击“测试连接”会调用服务商接口，但不会保存；点击“保存配置”会写入根目录 `.env` 并立即更新当前知识库及工作流使用的模型配置。页面不会回显已保存密钥。配置接口仅接受来自本机且带专用请求头的请求；服务应绑定 `127.0.0.1`，不要把配置页暴露到公网。两套配置可以指向相同或不同的服务商。

保存配置本身不代表模型已连通，请使用页面上的连接测试核验。尚未填写真实 API 时，文档上传、解析、分块与管理可运行，状态为 `pending_embedding`；向量化与检索返回 `EMBEDDING_NOT_CONFIGURED`，有检索结果但未配置问答模型时返回 `LLM_NOT_CONFIGURED`。测试中的模型替身只用于验证流程，**不代表真实模型已经接通**。已有知识库向量时，系统会阻止直接更换 Embedding 地址或模型；应先删除旧的已索引文档，再重新上传并建立索引，避免混用不同模型的向量。

启动后访问 `http://127.0.0.1:8004/` 使用 Web 前端；`http://127.0.0.1:8004/api/health`、`http://127.0.0.1:8004/api/health/db` 和 `http://127.0.0.1:8004/docs` 分别用于服务、数据库健康检查与 Swagger 调试。如 8004 端口已被占用，可把命令中的端口改为其他未占用端口。前端通过同源 `/api/v1` 调用后端，不需要单独启动前端服务器。普通健康检查不依赖 MySQL；数据库健康检查在数据库不可用时返回 HTTP 503。

### 已实现的业务接口

所有业务接口以 `/api/v1` 开头，可在 Swagger `/docs` 中填写参数并调试。成功与失败均返回 `code`、`message`、`data`、`meta` 四个字段；列表的 `meta` 含 `page`、`page_size`、`total`。分页默认每页 20 条、最多 100 条。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /students`、`GET /students`、`GET /students/{id}`、`PATCH /students/{id}` | 新增、分页浏览、查看及修改考生信息。 |
| `GET /universities`、`GET /majors` | 按院校、专业、省份、年份、城市和选科等条件查询。 |
| `GET /admission-plans`、`GET /admission-records` | 按省份、年份、院校、专业及选科条件查询招生计划和历年录取数据。 |
| `POST /plans`、`GET /plans?student_id=...`、`GET /plans/{id}` | 保存草稿方案、查看考生历史方案及其明细。 |
| `POST /knowledge-documents`、`GET /knowledge-documents`、`GET /knowledge-documents/{id}` | 上传 PDF/DOCX/TXT，查看文档及处理状态。上传限 10 MB，并填写文档类型与来源名称。 |
| `POST /knowledge-documents/{id}/index`、`DELETE /knowledge-documents/{id}` | 配置 Embedding 后向量化待处理文档；删除文档及其索引。 |
| `POST /knowledge-search`、`POST /knowledge-qa` | 相似度检索；基于检索片段回答问题并返回候选来源。请求体为 `{"question":"...","limit":5}`。 |
| `GET /model-settings`、`PUT /model-settings/{kind}`、`DELETE /model-settings/{kind}`、`POST /model-settings/{kind}/test` | 本机读取配置状态、保存、清除及测试连接；`kind` 为 `llm` 或 `embedding`，读取结果不含密钥。 |
| `POST /workflow-runs`、`GET /workflow-runs/{id}` | 启动六 Agent 工作流，查看执行状态、节点输入输出、错误、风险报告及生成的方案。 |

`POST /plans` 是人工草稿保存接口，要求调用方填写梯度、分数、理由与依据，不自动计算。自动推荐通过 `POST /workflow-runs` 执行，结果保存为 `generated` 方案。

知识库原文保存在 `storage/uploads`，清洗后的分块与来源元数据保存在 MySQL，向量保存在 `storage/chroma`；两个运行时目录都不提交仓库。检索返回文档名、来源、适用年份、页码/章节和相关片段。问答只把检索片段作为上下文；无可用资料时明确说明不能据此回答。扫描版 PDF 尚不支持 OCR，上传时会提示无可提取文本。上传者提供的来源信息必须自行核验，不能自动视为官方资料。

### 六 Agent 工作流

在 Swagger 中先创建考生，再向 `POST /api/v1/workflow-runs` 提交 `{"student_id": 1, "max_adjustments": 2}`（替换为实际考生 ID）。执行依次经过考生画像、任务规划、数据检索、院校匹配、志愿推荐和风险评估；`GET /api/v1/workflow-runs/{id}` 返回持久化的节点状态、输入输出摘要、错误及方案。运行方式为同步请求，工作流进度可在完成后通过事件记录查看。

数据检索节点实际查询 MySQL 的当年招生计划和历年最低位次，并调用知识库相似度检索。未配置 Embedding 或知识库无资料时，会记录数据缺口，不能把未检索到的政策当作依据。风险复核检查选科、年份、梯度、资料缺口及模拟数据。仅在缺失梯度且扩大历史年份可能补足候选时调整，最多 2 次。

### 志愿匹配算法

1. **硬约束**：招生计划必须匹配考生省份和报考年份，院校及专业资料年份也须一致；招生计划与专业的选科要求均须满足。要求缺失或无法识别时按不满足处理。缺少可用历史最低位次的候选进入 `unranked_candidates`，只提示原因，不进入正常推荐。
2. **位次依据**：取同省份、院校、专业和批次的最近最多三条有效历史最低位次，计算中位数 `参考位次`；`位次比值 = 参考位次 / 考生位次`。默认低于 0.9 为“冲”，0.9 至低于 1.2 为“稳”，不低于 1.2 为“保”。不同年份的招生口径可能变化，这只是演示性规则，不是录取概率。
3. **加权评分**：`总分 = 位次分 + 兴趣分 + 城市分 + 风险偏好分 + 数据质量分`。默认位次分为 `50 × clamp(位次比值 - 0.5, 0, 1)`；兴趣词匹配专业名或类别得 15 分；城市命中得 10 分。风险偏好分最高 10 分：保守偏好倾向“保”，积极偏好倾向“冲”，均衡偏好倾向“稳”。数据质量分最高 15 分，按历史年份和来源完整性折减；任一来源标记为模拟时，其系数最高为 0.25。五项权重、分档阈值可在 `.env` 调整，权重总和不为 100 时服务拒绝启动。
4. **解释与风险**：每个推荐返回分项得分、逐年历史位次及来源、位次比值、推荐理由和风险说明。只有一年历史数据、历史位次波动较大、数据过旧或使用模拟数据时明确警示；模拟数据的单项风险等级为 `unknown`。风险偏好还决定每档最多保留的数量；不足时不补造候选。

测试样例：上海 2026 年、位次 10000、选科“物理 化学”、兴趣“计算机”、目标城市“上海”、均衡风险偏好。模拟院校 B 的 2025 年最低位次为 6500，比值 0.65，归“冲”；默认权重下分项为位次 7.5、兴趣 15、城市 10、风险偏好 5、数据质量 3.75，总分 **41.25**。数据质量低分源于模拟数据标记。完整测试用例位于 `tests/test_matching_rules.py` 和 `tests/test_workflow.py`。

**匹配评分不是录取概率，模拟数据不可用于实际志愿填报，系统不保证录取结果。**

当前没有真实模型 API 配置。工作流采用可解释的确定性规划与理由生成；测试使用模型替身验证 Chroma 调用，不代表真实模型已接通。`sql/seed_simulated_data.sql` 中新增的院校、专业与位次仍全部标记为模拟数据，只能用于演示和测试，不可用于实际志愿填报。

## 7. 数据说明

### 院校招生数据

应包括院校基本信息、专业信息、分省招生计划、选科要求和招生章程等内容。正式使用时应优先来自教育考试机构、院校招生官网、教育部阳光高考等可核验渠道，并保留来源链接、适用省份、适用年份和更新时间。

### 历史录取数据

应包括分省、分年份、分院校和分专业的录取分数、位次等可用字段。由于不同省份的招生批次、选科要求和数据口径可能不同，导入前需校验数据口径、完整性和时效性，并在推荐结果中说明数据适用范围。

### 政策知识库

知识库拟收录招生政策、招生章程、专业介绍等文本资料。资料入库前应保留文档来源、发布日期、适用地区和版本信息；检索结果只作为辅助解释，不替代官方政策文本。

### 当前数据状态

当前仓库尚无正式招生数据、历史录取数据或知识库资料。`sql/seed_simulated_data.sql` 中的院校、专业、招生计划及历史录取记录均为**模拟数据**，仅供数据库结构和开发测试使用；不能据此做出确定性录取判断。
