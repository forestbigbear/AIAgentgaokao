# 传统规则与多智能体工作流对比实验

## 1. 目的与数据边界

依据开题报告的实验要求，在**同一考生条件、同一招生数据**下比较：硬条件满足率、专业偏好匹配度、风险/数据缺口识别和响应时间。本次只比较当前 LangGraph 工作流与一个明确实现的位次规则基线；本机未配置真实 LLM/Embedding，因此不能把差异归因于大语言模型。

数据为 `sql/seed_simulated_data.sql` 对应的上海 2026 年 9 条候选计划，历史位次取最近两年。院校、专业和位次均标记为**模拟数据**，不是官方数据。运行前脚本验证了预期候选数量、名称和来源。数据快照 SHA-256：`ed5eb38af8805a952ba45bbcf9217dec6113b8be42d9b39d5f9bb3122d188cce`。原始逐次结果保存在 `docs/实验原始结果.json`。

## 2. 方法与指标定义

三组考生均为上海、2026 年、成绩 510、位次 10000、选科“物理 化学”；只改变兴趣、目标城市与风险偏好。每组在相同数据库快照上分别运行两种方法 5 次。为使检索窗口一致，工作流设置 `max_adjustments=0`；有限调整能力由单独工作流测试验证。两方法采用相同选科/省份/年份硬约束、两年历史窗口、冲稳保位次分界（0.9、1.2）及风险偏好名额。

- **传统规则基线**：从 MySQL 检索候选，过滤硬条件和无有效历史位次者；冲档优先选位次比值较高者，稳档选最接近 1 者，保档选位次比值较高者。按相同梯度名额取结果。附带选科排除、模拟来源、单年/过旧历史与梯度缺口的基础检查；没有 RAG 检查。基线未调用工作流或模型。
- **多智能体方法**：经 FastAPI `POST /api/v1/workflow-runs` 执行六节点 LangGraph 工作流；MySQL/RAG 检索、加权评分、梯度方案、风险复核和持久化都在请求内完成。当前 RAG 因未配置 Embedding 返回明确数据缺口。
- **硬条件满足率** = 满足报考省份、年份、院校/专业年份、选科和有效历史位次的推荐条目数 / 推荐总条目数；按原始 MySQL 候选复核。
- **专业偏好匹配度** = 推荐专业名称或类别命中考生至少一个兴趣词的条目数 / 推荐总条目数。此处是字面命中率，不是用户满意度。
- **风险识别率** = 检出的适用风险/数据缺口类别数 / 从原始字段与配置独立列举的适用类别数。类别包括选科排除、模拟来源、仅一年历史位次、过旧历史、梯度缺口和知识库不可用；本次每组实际适用前述中的四类：选科排除、模拟来源、单年历史、知识库不可用。按类别计数，不把同类的每条告警重复计数。
- **响应时间**：`perf_counter_ns()` 记录各方法调用耗时，报告 5 次中位数；每组交替先运行基线和工作流以减轻顺序影响。工作流耗时包含进程内 TestClient HTTP 请求、MySQL 写入及 RAG 错误处理；基线耗时包含 MySQL 检索和进程内计算，不包含 HTTP 或持久化。这是两种实现的实际执行成本，**不是同等服务边界的纯算法速度比较**。

## 3. 实测结果

执行环境为 Windows、Python 3.12.10、MySQL 9.7.4。每组 5 次运行均返回相同推荐集合与指标；工作流每次记录 6 个完成的 Agent 事件。表中条目及风险计数按每组一次结果列示，耗时为 5 次中位数。

| 考生条件 | 方法 | 推荐数 | 硬条件满足 | 兴趣命中 | 风险类别识别 | 中位耗时 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 均衡 / 计算机 / 上海 | 多智能体 | 6 | 6/6 | 2/6（33.3%） | 4/4 | 28.483 ms |
| 均衡 / 计算机 / 上海 | 传统规则 | 6 | 6/6 | 2/6（33.3%） | 3/4 | 0.993 ms |
| 保守 / 计算机 / 上海 | 多智能体 | 5 | 5/5 | 2/5（40.0%） | 4/4 | 26.704 ms |
| 保守 / 计算机 / 上海 | 传统规则 | 5 | 5/5 | 1/5（20.0%） | 3/4 | 0.996 ms |
| 积极 / 软件 / 苏州 | 多智能体 | 5 | 5/5 | 1/5（20.0%） | 4/4 | 27.125 ms |
| 积极 / 软件 / 苏州 | 传统规则 | 5 | 5/5 | 1/5（20.0%） | 3/4 | 0.978 ms |

按三组不同画像合并（不把重复计时当作独立考生）：两方法硬条件均为 **16/16（100%）**；兴趣命中分别为 **5/16（31.25%）** 与 **4/16（25.00%）**；适用风险类别识别分别为 **12/12（100%）** 与 **9/12（75%）**。15 次耗时的合并中位数分别为 **26.971 ms** 与 **0.993 ms**；范围分别为 25.183–41.705 ms 与 0.742–1.432 ms。

保守偏好案例产生唯一的推荐集合差异：多智能体选入“模拟计算机科学与技术”，规则基线选入“模拟软件工程”。前者命中“计算机”兴趣，说明加权评分在此小样本下改变了选项；均衡和积极案例的推荐集合相同，仅顺序不同。两方法均排除了不满足物理/化学选科的历史类专业。

## 4. 解释与局限

1. 风险识别率的 1 类差异是“知识库不可用”。传统规则基线不访问 RAG，工作流会记录 `EMBEDDING_NOT_CONFIGURED`。这说明工作流更完整地暴露了当前系统的数据缺口，**不能证明其对真实招生风险的预测更准确**。
2. 两方法使用相同硬条件校验，因此均为 100% 在预期之内；不能据此比较录取效果。模拟数据没有真实录取结果标签，也没有正式政策校验。
3. 兴趣命中只是字符串匹配。3 个画像和 9 条候选规模很小，只有保守案例的集合发生变化；不能从 5/16 对 4/16 推断普遍优势或统计显著性。
4. 耗时的执行范围不同，且 TestClient 省去了真实网络传输；工作流还写入画像、事件和方案。不能把 26.971/0.993 的比值当作同条件算法速度差。需要同边界服务压测、更多样本和稳定环境才能形成性能结论。
5. 当前规划、匹配与推荐节点主要采用可解释的确定性规则；真实模型 API 尚未接通。本实验评估的是**现有六节点工作流及其规则评分**，不是 LLM 推理质量。

## 5. 复现

在项目根目录配置本地 `.env`，确保 MySQL 已初始化并导入明确标记的模拟数据后：

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m scripts.experiment --repeats 5
```

脚本 `backend/scripts/experiment.py` 在运行前核验 9 条候选的名称与模拟来源，记录快照哈希和逐次耗时，输出 `docs/实验原始结果.json`；其间创建的测试考生、工作流事件和方案在采样后清理。若招生数据已改动，脚本会拒绝沿用本次实验口径。该文件含完整逐次结果，可重新计算本报告数值。本系统仅提供志愿填报决策辅助，**不保证录取**。
