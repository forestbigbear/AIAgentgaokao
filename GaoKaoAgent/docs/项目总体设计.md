# 项目总体设计

## 1. 设计依据与范围

项目名称为“基于多智能体协作的高考志愿智能填报系统研究”。本设计以立题报告确定的研究方向为边界，以开题报告中更具体的技术路线、功能模块和进度安排为主要依据。

项目定位为高考志愿填报决策辅助系统，不是招生录取预测或录取承诺系统。系统须展示数据来源、适用年份、更新时间和风险提示；任何推荐结果均需提示用户以教育考试机构、院校招生官网和教育部阳光高考等官方渠道的最新信息为准。

### 1.1 两份报告的核心要求提取

| 维度 | 立题报告 | 开题报告 | 本设计结论 |
| --- | --- | --- | --- |
| 研究目标 | 用多智能体、规则和 RAG 生成可解释的“冲、稳、保”方案。 | 强调从考生输入到风险复核的完整 Web 系统。 | 实现可演示的决策辅助闭环，不承诺录取结果。 |
| 技术路线 | Python、FastAPI、HTML/CSS/JavaScript、LangChain/LangGraph、MySQL、RAG 与向量数据库。 | 明确六个 Agent、MySQL 结构化数据与 RAG 政策/专业文本检索。 | 严格采用指定技术栈；MySQL 使用 PyMySQL，不使用 ORM。 |
| 功能范围 | 考生画像、数据管理、推荐、风险、历史方案和测试分析。 | 进一步明确八项功能：考生、数据、工作流、推荐、风险、问答、方案、测试。 | 以开题报告的八项功能模块作为实现范围。 |
| 数据边界 | 可用模拟数据，但必须显著标注，不能冒充真实招生数据。 | 要记录来源、适用年份和更新时间。 | 数据模型、接口和页面均保留来源元数据与数据不足提示。 |
| 测试目标 | 功能、接口、工作流与传统规则法对比。 | 指标包括条件满足率、专业偏好匹配度、风险识别和响应时间。 | 在第八阶段建立自动化测试和实验统计。 |

## 2. 完整需求整理

### 2.1 业务功能

1. 考生信息管理：录入、校验、修改和展示结构化考生画像。
2. 院校专业数据管理：管理并按省份、年份、院校、专业和选科要求查询院校、专业、招生计划与历史录取数据。
3. 多智能体协作：展示六个 Agent 的状态、输入摘要、处理结果、异常信息和整体进度。
4. 院校匹配与志愿推荐：基于位次、选科、兴趣和城市偏好，生成有理由、依据和风险提示的冲稳保方案。
5. 风险评估：检查选科限制、数据完整性/年份和梯度合理性，给出风险等级与调整建议。
6. 智能知识问答：上传 PDF、DOCX、TXT，完成解析、分块、向量化、检索、问答及来源展示。
7. 志愿方案管理：保存、查看详情、查询历史和比较不同方案。
8. 系统测试与分析：测试接口、核心功能、工作流、RAG 和推荐算法，并与传统规则推荐做对比。

### 2.2 非功能约束

- 后端为 Python + FastAPI + Uvicorn 的 RESTful API，按路由、服务、数据访问、Agent、知识库与配置分层。
- 数据访问只用 PyMySQL 和参数化 SQL；不使用 SQLAlchemy 或其他 ORM。
- 前端只使用 HTML5、CSS3、原生 JavaScript 和可选 Bootstrap 5 CDN；不使用 npm、Vue、React、Angular、TypeScript、Vite、Webpack 或前端路由框架。
- 大模型通过环境变量配置的 API 调用；真实 API Key、数据库密码等敏感信息不得写入代码或提交仓库。
- Agent 不是固定文本模拟：每个节点必须基于共享状态、数据库/知识库检索结果或可配置的大模型 API 产生结果，并保留执行记录。

## 3. 系统总体架构

```text
浏览器（HTML / CSS / 原生 JavaScript）
        │ fetch() / RESTful JSON
        ▼
FastAPI 路由层
        │ 请求校验、统一响应、异常映射
        ▼
业务服务层 ──────────────── Agent 工作流层（LangGraph）
        │                         │
        │                         ├── 六个 Agent 节点与共享状态
        │                         └── 有限次数风险调整与执行日志
        ▼
数据访问层（PyMySQL / 参数化 SQL）      知识库服务（RAG）
        │                                      │
        ▼                                      ▼
MySQL                                   文档解析 / 分块 / Embedding / Chroma
```

### 3.1 后端分层职责

| 层级 | 职责 |
| --- | --- |
| API 路由层 | 接收请求、Pydantic 数据校验、调用服务、返回统一 JSON 响应。 |
| 服务层 | 编排考生、院校专业、方案、推荐和测试等业务规则，不直接拼接 HTTP 响应。 |
| 数据访问层 | 集中管理 PyMySQL 连接池和参数化 SQL，封装事务、查询和数据映射。 |
| Agent 工作流层 | 定义 LangGraph `State`、六个节点、条件边、最大调整次数和执行日志。 |
| 知识库层 | 文档上传、解析、分块、向量写入、相似度检索和含来源的回答生成。 |
| 配置与基础设施层 | 加载环境变量、日志、统一异常、文件存储路径和应用生命周期。 |

### 3.2 对外 API 边界

API 后续统一以 `/api/v1` 为前缀，主要资源为：`students`、`universities`、`majors`、`admission-plans`、`admission-records`、`recommendations`、`workflow-runs`、`knowledge-documents`、`knowledge-qa` 和 `plans`。请求与响应使用明确的 Pydantic 模型；错误响应包含业务错误码、消息和可选字段级错误信息。

## 5. MySQL 数据库设计

数据库采用 `utf8mb4` 字符集和 InnoDB 引擎。除明确为可空的业务字段外，关键关系字段均不为空；创建与更新时间统一保存。数据访问将通过 PyMySQL 连接池和参数化 SQL 完成。

### 5.1 核心表

| 表名 | 关键字段 | 说明与关系 |
| --- | --- | --- |
| `students` | `id`、`province`、`exam_year`、`score`、`rank_no`、`subject_combination`、`interests`、`target_cities`、`risk_preference` | 考生基础信息与偏好；JSON 字段仅保存可扩展的兴趣、城市列表。 |
| `student_profiles` | `id`、`student_id`、`profile_json`、`validation_warnings`、`generated_at` | 保存画像 Agent 生成的结构化画像和校验提示；关联 `students`。 |
| `universities` | `id`、`name`、`province`、`city`、`level`、`source_name`、`source_url`、`applicable_year`、`updated_at` | 院校主数据与来源元数据。 |
| `majors` | `id`、`university_id`、`name`、`major_code`、`category`、`subject_requirements`、`source_name`、`source_url`、`applicable_year` | 院校下的专业及选科要求；关联 `universities`。 |
| `admission_plans` | `id`、`university_id`、`major_id`、`province`、`exam_year`、`batch_name`、`planned_count`、`subject_requirements`、`source_name`、`source_url`、`updated_at` | 分省、分年招生计划；关联院校和专业。 |
| `admission_records` | `id`、`university_id`、`major_id`、`province`、`exam_year`、`batch_name`、`min_score`、`min_rank_no`、`source_name`、`source_url`、`updated_at` | 历年录取数据；记录数据口径和适用范围。 |
| `recommendation_plans` | `id`、`student_id`、`exam_year`、`status`、`workflow_run_id`、`summary`、`created_at` | 一次推荐的主记录；关联考生及工作流。 |
| `recommendation_items` | `id`、`plan_id`、`university_id`、`major_id`、`tier`、`match_score`、`reason_text`、`evidence_json`、`risk_level`、`risk_notes` | 推荐明细；`tier` 限定为冲/稳/保。 |
| `workflow_runs` | `id`、`student_id`、`status`、`current_node`、`adjustment_count`、`max_adjustments`、`started_at`、`finished_at`、`error_message` | LangGraph 一次运行的状态汇总。 |
| `workflow_events` | `id`、`workflow_run_id`、`agent_name`、`event_type`、`status`、`input_summary`、`output_summary`、`error_message`、`created_at` | Agent 状态、主要结果和异常，用于工作流展示；关联 `workflow_runs`。 |
| `knowledge_documents` | `id`、`original_name`、`file_type`、`storage_path`、`document_type`、`source_name`、`source_url`、`applicable_region`、`applicable_year`、`published_at`、`ingest_status`、`uploaded_at` | 已上传知识文档的来源与处理状态。 |
| `knowledge_chunks` | `id`、`document_id`、`chunk_index`、`content`、`page_or_section`、`chroma_id` | 文本分块元数据；向量本体由 Chroma 保存；关联文档。 |
| `operation_logs` | `id`、`operation_type`、`target_type`、`target_id`、`detail_json`、`created_at` | 可选审计记录；仅保留系统必要操作，不超出课题范围。 |

### 5.2 关系、索引与约束

- `universities` 1:N `majors`，`students` 1:N `student_profiles`，`students` 1:N `recommendation_plans`。
- `recommendation_plans` 1:N `recommendation_items`；`workflow_runs` 1:N `workflow_events`；`knowledge_documents` 1:N `knowledge_chunks`。
- 为 `admission_plans` 和 `admission_records` 建立复合索引：`(province, exam_year, university_id, major_id)`；为院校名称、专业名称建立检索索引。
- 为 `recommendation_items(plan_id, tier)`、`workflow_events(workflow_run_id, created_at)`、`knowledge_chunks(document_id, chunk_index)` 建立索引。
- `source_name`、`source_url`、`applicable_year` 和 `updated_at` 是招生数据的必要元数据；缺失时不得在推荐页表现为完整官方数据。
- 外键默认使用 `RESTRICT` 或按业务需要的受控删除，避免误删已被方案引用的数据。实际 DDL 将在第二阶段创建并通过 MySQL 验证。

### 5.3 数据与连接策略

- 初期使用 `sql/seed_simulated_data.sql` 导入**明确标记为模拟数据**的最小可演示数据集，字段中保留 `source_name='模拟数据'` 与适用年份。
- 后续正式数据导入前，先保存来源链接、发布日期、适用地区、适用年份和更新时间，再进行去重、字段校验和入库。
- 应用启动时创建有限大小的 PyMySQL 连接池；每个请求从池获取连接、完成后归还。写操作通过事务处理，所有 SQL 均使用占位符参数化。

## 6. 六个 Agent 与协作工作流设计

### 6.1 共享状态

LangGraph 状态至少包含：`workflow_run_id`、`student_input`、`student_profile`、`validation_issues`、`task_plan`、`structured_data`、`knowledge_evidence`、`match_results`、`recommendations`、`risk_report`、`adjustment_count`、`max_adjustments`、`agent_events`、`errors` 与 `final_status`。每个节点只更新其负责部分，并追加不可变的事件记录。

### 6.2 Agent 职责与输入输出

| Agent | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| 考生画像 Agent | 原始考生字段 | 校验省份、年份、分数、位次、选科、兴趣、城市和风险偏好；识别缺失/异常。 | 标准化画像、字段错误和警告。 |
| 任务规划 Agent | 考生画像及用户需求 | 决定结构化数据检索条件、知识库检索主题和匹配优先级；缺数据时调整检索任务。 | 任务计划与执行顺序。 |
| 数据检索 Agent | 任务计划 | 用 MySQL 查询计划/录取数据；用 Chroma 检索政策和专业资料；保留来源、年份和缺失项。 | 结构化数据、知识证据、数据缺口。 |
| 院校匹配 Agent | 画像、检索结果 | 先排除不满足选科要求者，再按位次、兴趣、城市与数据质量加权评分。 | 候选集、分数与评分依据。 |
| 志愿推荐 Agent | 匹配结果 | 按规则将候选分入冲、稳、保梯度，形成推荐理由、数据依据和初始风险提示。 | 推荐方案明细。 |
| 风险评估 Agent | 推荐方案、画像、数据元信息 | 检查选科、数据缺失/过期、梯度重复或失衡及风险偏好匹配情况。 | 风险等级、问题列表、建议和是否调整。 |

### 6.3 工作流与有限调整

```text
开始
  -> 考生画像 Agent
  -> [输入严重错误？] 是 -> 结束：返回校验错误
                     否 -> 任务规划 Agent
                         -> 数据检索 Agent
                         -> 院校匹配 Agent
                         -> 志愿推荐 Agent
                         -> 风险评估 Agent
                         -> [需要调整且 adjustment_count < max_adjustments？]
                               是 -> 任务规划 Agent（增加 adjustment_count）
                               否 -> 结束：输出方案、风险报告和执行日志
```

默认 `max_adjustments` 设计为 2，作为可配置上限。只有“可通过重新规划改善”的风险，例如候选梯度失衡、可替换候选的选科冲突或检索范围不足时，才允许回到任务规划节点。严重输入错误、没有可用数据或达到最大次数时，流程结束并明确提示原因，绝不无限循环。

### 6.4 推荐评分和梯度原则

1. 硬约束：省份、报考年份、选科要求及有效招生计划不匹配时直接排除。
2. 软评分：以位次相对历史最低位次的机会评估为主，叠加专业兴趣、目标城市、数据完整度与时效性等可解释权重。
3. 梯度划分：根据相对位次机会值和风险偏好区分冲、稳、保；阈值与权重在配置中集中管理，并在测试中使用模拟数据验证。
4. 传统规则对比：保留不调用 LLM 的规则推荐基线；多智能体方案与其使用相同输入和候选数据，对比条件满足率、偏好匹配、风险识别和响应时间。

## 7. RAG 知识库设计

1. 上传：只接收 PDF、DOCX、TXT，并对文件类型、大小和存储路径进行校验。
2. 解析：提取正文及页码/章节等可定位信息；失败时将失败原因写入 `knowledge_documents.ingest_status`。
3. 分块：按标题和文本长度进行带重叠的分块，保留原文档、页码或章节、年份和来源元数据。
4. 向量化：通过配置的 Embedding 服务生成向量，写入 Chroma；MySQL 仅保存分块、来源和 `chroma_id`。
5. 检索问答：根据问题检索相关分块，将证据及来源传入大模型 API 生成回答；无足够证据时明确说明不能据此回答。
6. 展示：问答接口返回答案、引用片段、文档名、来源、适用年份和定位信息，前端展示可追溯来源。

## 8. 前端技术方案与页面规划

前端采用静态 HTML 页面、统一 CSS 和按页面拆分的原生 JavaScript。公共导航和请求封装放入 `common.js`；页面通过 `<a>` 跳转，通过 `fetch()` 调用 API；Bootstrap 5 仅可通过 CDN 辅助表格、表单和按钮样式，不引入任何构建过程或 npm 依赖。

| 页面 | 文件建议 | 主要内容与交互 |
| --- | --- | --- |
| 系统首页 | `frontend/index.html` | 项目说明、功能入口、模拟数据与免责声明提示、必要统计。 |
| 考生信息管理 | `pages/student.html` + `student.js` | 信息录入、前端基础校验、保存、修改和画像展示。 |
| 院校专业查询 | `pages/universities.html` + `universities.js` | 省份、年份、院校、专业、选科条件筛选和数据来源展示。 |
| 智能志愿推荐 | `pages/recommendation.html` + `recommendation.js` | 启动工作流、轮询/获取运行结果、冲稳保方案和依据。 |
| 风险评估结果 | `pages/risk.html` + `risk.js` | 展示风险等级、原因、数据缺口和调整建议。 |
| 多智能体工作流 | `pages/agents.html` + `agents.js` | 展示六个 Agent 的状态、结果摘要、异常和工作流进度。 |
| 政策知识库问答 | `pages/knowledge.html` + `knowledge.js` | 文档上传、处理状态、提问、答案与来源。 |
| 历史方案管理 | `pages/history.html` + `history.js` | 历史列表、详情、保存和两个方案的结构化比较。 |

所有页面共享 `css/style.css`，坚持后台管理风格：固定导航、清晰表单、表格和少量信息卡片；不增加前端状态管理、复杂动画或与课题无关的页面。
